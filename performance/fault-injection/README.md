# Stage 4 fault-injection suite

This suite exercises the reliability claims from stages 2 and 3 against the packaged application. It produces HTTP bodies, Prometheus snapshots, database snapshots, RabbitMQ queue snapshots, a JSON summary, and a Markdown report under `performance/results/fault-injection-*`.

## Covered scenarios

1. `cache-cross-instance`: instance B warms an Agent in Caffeine, instance A updates it, and B must observe the new value through Redis/Redisson invalidation within 5 seconds. The exact convergence time is recorded.
2. `redis`: after the 2-second authentication L1 TTL expires, Redis is stopped. `/api/auth/me` must stay HTTP 200 through database fail-open, an L2 error metric must be present, and the endpoint must still succeed after Redis recovers.
3. `rabbitmq`: RabbitMQ is stopped before an upload. The request must return HTTP 202, Outbox must record a failed publish, then retry to `PUBLISHED` and drive the document to `READY` after RabbitMQ recovers.
4. `worker-restart`: the Mock delays Embedding while a document is `PROCESSING`; the worker is terminated with `SIGKILL`. RabbitMQ must redeliver it, the processing fence must advance without consuming another logical attempt, and the document must reach `READY`.
5. `embedding-timeout`: the Mock returns HTTP 408. Exactly three finite attempts must run, the exhausted delivery must enter the parking queue, and a manual retry must reach `READY` after the Mock is restored.

The HTTP 408 scenario represents an upstream timeout response. A 4xx timeout is intentional: Spring AI internally retries transient 5xx responses, while this drill isolates the application's three delivery attempts. It verifies application retry/parking behavior, not the HTTP client's socket timeout against a TCP black hole.

## Prerequisites

- Java 21, Docker Compose, `curl`, `jq`, `python3`, and `shasum`.
- A current packaged JAR at `target/enjoy-agent-0.0.1-SNAPSHOT.jar`.
- The fixed 64 KiB fixture generated by `performance/fixtures/generate-document.py`.
- Ports 18081, 18082, and 18083 must be free. Ports 8080 and 18080 are not used.

Build and generate the fixture if necessary:

```bash
./mvnw clean package
python3 performance/fixtures/generate-document.py \
  --bytes 65536 \
  --output performance/fixtures/generated/document-64k.txt
```

## Run

Run all scenarios from the backend project root:

```bash
./performance/fault-injection/run-fault-drills.sh all
```

Run one or more selected scenarios:

```bash
./performance/fault-injection/run-fault-drills.sh cache-cross-instance redis
./performance/fault-injection/run-fault-drills.sh rabbitmq worker-restart embedding-timeout
```

Useful overrides:

```bash
FI_APP_PORT=18081 \
FI_SECONDARY_APP_PORT=18083 \
FI_EMBEDDING_PORT=18082 \
FI_DOCUMENT_TIMEOUT_SECONDS=120 \
FI_CACHE_CONVERGENCE_TIMEOUT_SECONDS=5 \
FI_JAR=/absolute/path/to/enjoy-agent.jar \
./performance/fault-injection/run-fault-drills.sh all
```

The full suite normally takes 4–7 minutes on the local development stack. Redis and RabbitMQ are briefly stopped, so do not run it concurrently with another workload using the same Compose services.

## Isolation and cleanup

- A unique test user/tenant and run-specific document/Agent records are created for auditability. Existing rows are not changed or deleted.
- Every run uses a unique durable RabbitMQ exchange, main queue, parking queue, and routing keys.
- The suite stops only its own Java/Python processes and deletes only its run-specific RabbitMQ topology.
- If a run aborts mid-task, only that run's unfinished Outbox rows are removed and its active documents are marked `FAILED/FAULT_DRILL_ABORTED`; this prevents a later application instance from publishing abandoned test work through a different topology.
- It records which Compose services were running before the suite. Services that were originally running are restored to running; services started by the suite are stopped afterward.
- It never invokes `docker compose down`, removes a volume, purges a shared queue, or deletes existing application data.
- An `EXIT` trap performs recovery and renders a failure report even when an assertion stops the suite.

The final path is printed as `Results: ...`. Inspect `report.md` first, then use the referenced evidence files for details.
